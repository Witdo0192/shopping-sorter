# Как устроен код

Расширение работает без сборки. Для запуска достаточно загрузить папку в Chrome.
Node.js нужен только разработчику для проверок. DevDependencies используются
линтером; у самого расширения runtime-зависимостей по-прежнему нет.

## Границы частей

```text
manifest.json                 порядок загрузки
content.js                    запуск, конфигурация, сообщения, наблюдение страницы
search.js                     синтаксис поисковых выражений
src/content/
  config/                     нормализация сайтов, единиц и доменов
  selectors/                  подбор и эвристики распознавания
  products/                   поля, количества, метрики, сбор, фильтрация и сортировка
  storage/                    сохранённые метаданные и миграция
  images/                     изображения и визуальное сходство
  ui/
    products-panel.js         состояние панели и соединение частей
    *-view.js                 отображение текущих и сохранённых списков
    filter-controls.js        поля и кнопки фильтров
    search-*.js               редактор, подсказки и выбор товаров
    delivery-calendar.js      календарь
    saved-queries.js           сохранённые запросы
    product-folders.js         папки
    product-transfer.js        импорт/экспорт
    lifecycle.js               очистка внешних событий и временного UI
background.js                 изображения в IndexedDB и сообщения
popup.js / settings.js        отдельные страницы расширения
```

Точные файлы и функции перечислены в [карте кода](code-map.md).
Размер файла — ориентир; отдельная ответственность и понятные связи важнее
произвольного ограничения числа строк. Picker пока самый большой файл
(около 1 500 строк), но посвящён одной функции — подбору селекторов.

## Как соединяются части панели

UI создаётся функциями вида `createSearchProductsView(dependencies)`.
Каждая функция хранит внутреннее состояние в замыкании и возвращает нужные
элементы, действия и, если есть ресурсы для очистки, `destroy()`.

Список после фильтрации заменяется новым массивом. Поэтому зависимость
передаётся через геттер, а не копируется при создании:

```js
const view = createSearchProductsView({
    get currentTiles() { return currentTiles; },
    set currentTiles(value) { currentTiles = value; },
    // Остальные зависимости указаны в месте создания view.
});
```

Геттер читает актуальное значение, сеттер возвращает изменения владельцу.
Обычные DOM-узлы и функции также перечислены явно. У разных частей свой
набор зависимостей; общего объекта со всем содержимым панели нет.

Не делайте `const { currentTiles } = dependencies` внутри view:
после замены массива эта переменная станет устаревшей копией.
Для возвращаемых изменяемых свойств действует то же правило:
`panelTools.debugMode` и `attributeSuggestions.attributeSuggestCache`
нужно читать через интерфейс, а не один раз извлекать в переменную.

## Кто владеет состоянием

| Состояние | Владелец |
| --- | --- |
| Конфигурация, включение, наблюдение страницы, флаги счётчика | `content.js` |
| Собранные карточки | `seenTiles` в runtime; сбор — `products/collection.js` |
| Кэш метрик и единиц | `products/metrics.js` |
| Сохранённые ключи и наблюдение изображений карточек | `products/collection.js` |
| Очередь обновлений сохранённых метаданных | `storage/saved-products.js` |
| Активная вкладка, режим, текущие списки и общее состояние группировки | `ui/products-panel.js` |
| Настройки и выбор дат календаря | `ui/delivery-calendar.js` |
| Сохранённые запросы и состояние их меню | `ui/saved-queries.js` |
| Клоны текущих карточек | `ui/search-products-view.js` |
| Кэш вариантов автодополнения | `ui/attribute-suggestions.js` |
| Настройки отображения бейджей | `ui/unit-badges.js` |

Нижний слой пока использует общую область обычных content scripts:
`SELECTORS`, `UNITS`, `seenTiles`, сервисные функции товаров и хранения.
Это осознанная совместимость с существующим запуском без сборки;
полной изоляции через imports/exports здесь нет.
Новая часть UI получает состояние другой части через интерфейс,
а не добавляет ещё одну глобальную переменную.

## Загрузка и закрытие

Файл должен присутствовать в `manifest.json → content_scripts[0].js`.
Скрипты объявляют функции и начальное состояние; запуск обработки страницы,
загрузка предпочтений бейджей, миграция и начальный кэш вызываются из `content.js`.
Не переносите эти вызовы между файлами без проверки порядка инициализации.

При повторном открытии панели сначала вызывается закрытие прежнего экземпляра.
Закрытие возвращает прокрутку, удаляет DOM/стили и вызывает очистку частей.
`createUiLifecycle()` помогает удалить обработчики document/window и временные
меню. Отложенная регистрация события после destroy сразу очищается.

Runtime общается с открытой панелью через короткие callbacks
`window._ssClosePopup`, `window._ssRefreshSearch`, `window._ssApplyFilters`.
Они очищаются при закрытии. Это внутренние связи content script.
Popup и settings взаимодействуют через Chrome messages/storage.

## Как продолжать через обычный чат

1. Найдите задачу в карте: например, календарь, цена за единицу или экспорт.
2. Передайте соответствующий файл и место его создания/вызова.
3. Если чат просит зависимость, передайте её из карты; весь проект обычно не нужен.
4. Попросите сохранить формат storage, сообщения и постороннее поведение.
5. Примените правку, перезагрузите расширение и страницу, проверьте свой сценарий.
6. Обновите карту при переносе ответственности и текущий статус после проверки.

Примеры: оформление календаря — delivery-calendar и panel-styles;
алгоритм диапазона цены — filtering и metrics;
вид одной карточки — product-card;
порядок и группировка списка — соответствующий view и sorting.

## Проверки разработчика

Node.js: 20.19+ в ветке 20, 22.13+ в ветке 22 или 24+.
После клонирования из корня проекта:

```powershell
npm ci
npm run check
```

`npm run check` запускает ESLint и тесты. Отдельно доступны `npm run lint`
и `npm test`. Для запуска расширения установка devDependencies не требуется.

`eslint.config.mjs` содержит набор правил ошибок без форматирования. Парсер
Espree извлекает верхние объявления content scripts из файлов manifest,
чтобы `no-undef` распознавал общие функции, но не пропускал произвольные опечатки.
Popup, settings, background и Node-файлы имеют отдельные области глобальных имён.
`no-use-before-define` проверяет обращения до объявления в той же области;
безопасные поздние чтения из callback/геттеров внешних областей допускаются.
Это не анализ момента вызова callback или загрузки скриптов.

Тесты проверяют сочетание фильтров, изменение состояния, соединение частей панели,
порядок тестовых товаров после нажатия сортировки, закрытие и повторное открытие.
UI-тесты используют небольшой имитатор DOM/Chrome API, поэтому не подтверждают
разметку магазина, внешний вид, виртуализацию, сетевые изображения и импорт файлов.
Эти сценарии проверяются в Chrome по [текущему состоянию](current-state.md).

После переноса файла дополнительно проверьте его наличие в manifest,
синтаксис через `node --check путь/к/файлу.js` и `git diff --check`.
